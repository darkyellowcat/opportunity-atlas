# 机会路标

给计算机学生的竞赛、科研与开源活动指南。

从兴趣方向寻找具体赛道或课题，也可以用成长地图按想做的事发现机会，选择「参加比赛」后可组合参赛方式与兴趣方向，例如筛选能单人参加的硬件或设计比赛。卡片保留届次、参与渠道、人工核验日期和官方来源。收藏仅存于当前浏览器，导出的日历文件是当次数据快照。

## 本地预览

站点由静态 HTML、CSS 和 JavaScript 组成，仓库已包含活动详情页。安装 Python 3 后，在仓库根目录启动预览。

```powershell
py -3 -m http.server 8000 --bind 127.0.0.1
```

macOS 或 Linux 可用 `python3 -m http.server 8000 --bind 127.0.0.1`。打开 [本地首页](http://127.0.0.1:8000/)，按 Ctrl+C 停止服务。

## 首次推送与发布

首次提交应包含首页及其脚本和样式、`opportunities/` 下的静态页面、维护工具 `tools/`、`.nojekyll` 和 `.github/`。根目录的 `.gitignore` 会跳过本地巡查报告和工具缓存。推送后可从 `main` 分支根目录发布站点。具体命令见[首次推送与 Pages 发布指南](docs/publishing.md)。

## 接收推荐与纠错

在接收反馈的 GitHub 仓库中打开 **Settings → General → Features → Issues**，并将 `.github/ISSUE_TEMPLATE/` 提交到默认分支。标准 `用户名.github.io/仓库名/` 项目站会连接对应仓库，`用户名.github.io` 个人站会连接同名仓库。使用自定义域名时，在发布目录的 `catalog.js` 中将 `window.ATLAS_REPOSITORY` 设为实际的 `所有者/仓库名`。

读者可在「推荐与纠错」阅读教程，点击按钮直接打开 GitHub 的推荐或纠错模板。从具体活动的「纠正这条信息」进入时，纠错标题会带上活动名称。登录 GitHub 后，每个 Issue 写一件事，在标题写明活动和事项。

- 推荐用 `suggest.md`。写出活动名称、主办方公告链接，有余力时补一句哪些学生可以参加。
- 纠错用 `correct.md`。指出站内哪一项需要改、应改成什么，尽量附上对应届次的官方依据。如果只是链接失效，贴失效地址即可。

公开仓库会显示 Issue 原文和提交账号。反馈只需公开活动资料。维护者核实后更新站点，并可在原 Issue 留下处理结果。

## 更新活动

选取案例以公开的活动规则和参与渠道为依据。发布条目时，请省略维护者或推荐人的个人背景、账号和联系方式。

- 数据在 `programs.js`、`additions.js` 和 `extras.js`。以已有条目为模板，为每项保留稳定的 `id` 和可访问的官方来源。竞赛条目用 `contestFormat` 标注赛制，依据当届规则区分「个人赛」「团队赛」「个人或组队」「可单人组队」「按组别确定」。根据实际任务安排兴趣标签；同一大活动的新届次、选题及本校报名条件要写明适用范围。
- `events` 包含节点名称、范围和官方日期。只有整项活动的报名截止用 `deadline`；某所学校的选拔截止、材料提交、线下答辩各用独立节点，注明适用范围。仅公布日期时用 `YYYY-MM-DD`，公布了时刻要写 UTC 偏移，例如 `2027-01-28T15:00:00-05:00`。已公布的延期要保留出处与变更说明。
- 更改数据后运行 **`node tools/build-details.mjs`**，将生成的独立详情页一并提交。页面的收藏、比较和日历读取同一份活动数据。
- 人工核对了届次、资格和日期，再更新 `checked`。活动资格或截止时间仍不清楚时，可在卡片中写明具体缺口，留官方入口方便复查。

## 维护待核实清单

源码包带有 GitHub Actions 工作流 **官方来源巡查**。默认分支安装后，在 Actions 页面启用工作流（如 GitHub 提示），可用 **Run workflow** 首次建立基线。之后每天北京时间约 09:23 巡查。也可在仓库 Actions 变量中设置 `SOURCE_WATCH_ENABLED=false`，仅保留手动运行。

在 **Actions → 官方来源巡查 → 最近一次运行 → Summary** 看本次待办；同一份 Markdown 报告也可在该次运行的 Artifacts 下载。维护者应优先核对：

1. 招生通知、项目目录或官方 RSS 正文变化。相同变化保留在同一待办中，直到条目的人工核验日期推进。
2. 连续两个巡查日无法自动读取的来源。网页可能是动态页面、要求登录或临时故障；请打开原始公告人工检查。
3. 未来七天的具体节点，以及距上次人工核验超过默认 30 天的条目。

每项默认检查一个主来源；可在 `tools/watch-sources.json` 里给活动 ID 补充长期公告栏目或 RSS，或在条目上用 `watch` 配置地址、用 `reviewDays` 调整复核间隔。对于仅在公众号或校园网发布的通知，可在每周复核时人工查看。机器检查时间只代表本次读取，不会自动改写站点或提升人工核验日期。

巡查记录在 Actions 缓存中。新仓库、缓存过期后第一次运行会重新建立基线。GitHub 定时任务可能延迟；默认分支和仓库活跃要求见官方说明。

[GitHub Actions 定时任务说明](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule)
